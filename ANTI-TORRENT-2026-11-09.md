# Защита от торрентов и аномалий трафика: отзыв и план (2026-11-09)

Это решение по трём вопросам: брать ли vibehost-guard, оставлять ли nDPI и шейпер, как строить защиту от «вредителей». Код по этому плану пока не менялся, ждём вашего «да».

## 1. Отзыв о vibehost-guard

Проверен репозиторий `VIBEHOST-LLC/vibehost-guard`: склонирован во временную папку и только прочитан, ничего не запускалось. Ключевые выводы я перепроверил по коду.

**Что это.**
- 7 коммитов одного автора, 2026-10-27 — 2026-11-03.
- `guard.sh` (~590 строк sh) и демон `vh-dpid` на C (~1500 строк, статически собран с nDPI 6.0, LGPL-3.0). У `guard.sh` лицензии нет.
- Это агент хостинга VibeHost для дропа BitTorrent на любом Linux-сервере. Про Xray и Remnawave в коде нет ни слова.

**Как работает.**
- **iptables string-match** в цепочках INPUT/OUTPUT/FORWARD/DOCKER-USER: `BitTorrent protocol`, `d1:ad2:id20:`, `get_peers`, `announce_peer`, `info_hash=`, `/announce?`, magic UDP-трекера. Проверяются первые 4 КБ соединения, совпадение приводит к DROP пакета.
- **vh-dpid (nDPI через NFLOG)** со схемой strong/weak.
  - Strong: собственная проверка handshake, DHT, uTP и трекеров.
  - Weak: nDPI сказал «BitTorrent», но блокировка срабатывает только если уже был strong.
  - Блокирует соединение через conntrack-метку и запоминает пира на 30 минут.
- **Сканер портов:** порог 100 адресов или 200 пар адрес:порт в минуту при ≥50% отказов. По умолчанию только детект.

**Плюсы.** Аккуратный C-код (фиксированные таблицы, `-Werror`, тесты). systemd-хардениг: DynamicUser, только CAP_NET_ADMIN, seccomp, `CPUQuota=25%`, `MemoryMax=96M`. Продуманная защита от ложных срабатываний (strong/weak, игнор портов < 1024). DHT и UDP-трекеры ловит хорошо.

**Почему не ставить как есть.**

1. **Не знает, кто качает.** На OUTPUT источник — IP ноды. Email из access.log не используется, Remnawave API не вызывается. Пакет дропается, клиент ретраит, а пользователь остаётся безнаказанным и даже не попадает в список.
2. **Удалённое выполнение кода от root.** Каждые 5 минут heartbeat уходит на `api.vibehost.net`. Если облако отвечает новой версией, скрипт скачивает новый `guard.sh`, проверяет только синтаксис (`sh -n`) и запускает его от root. Облако же переключает режимы DPI (`off/shadow/enforce`) и скан-блока. Для ноды с панелью и пользовательскими данными это неприемлемо.
3. **Без облака nDPI выключен.** Режим DPI создаётся только ответом облака, без него работают лишь string-правила.
4. **Не видит часть трафика.** Не видит BT, ушедший через WARP, прокси-аутбаунды и SS-мосты (egress зашифрован), а также MSE/PE (шифрованный handshake) на OUTPUT.
5. **Ложные срабатывания.** Loose-сигнатуры (`info_hash=`, `/announce?`) режут обычные HTTP-страницы с magnet-ссылками.

**Вердикт:** как готовое решение не подходит. Как источник идей полезен: строгие сигнатуры DHT, uTP и UDP-трекера, схема strong/weak и детектор исходящего скана портов. Скан — реальная причина жалоб хостеру.

## 2. Встроенный torrent-blocker Remnawave

Источник: docs.rw, раздел Node Plugins. Требования: Xray ≥ 26.3.27, `NET_ADMIN`, nftables. На ваших нодах Xray 26.10.31, условие выполняется.

- Нода сама добавляет первым правилом `protocol: ["bittorrent"]` → blackhole `RW_TB_OUTBOUND_BLOCK`.
- При срабатывании нода кладёт **IP клиента** в nft-set на `blockDuration` и шлёт отчёт: вебхук `torrent_blocker.report` и `GET /api/node-plugins/torrent-blocker`.
- **Документация сама признаёт, что Xray-сниффер видит ~10–30% торрент-трафика.** Шифрованный BT, DHT и пиры по IP проходят.
- **Банит IP, а не пользователя.** Для CGNAT и мобильных это бьёт по невиновным. Пользователь остаётся ACTIVE.
- Сейчас у вас 0 отчётов (`total: 0`): плагин либо не включён, либо ничего не поймал.

Здесь вы правы: плагин один основной сценарий не закрывает. Но как **сильный сигнал** он полезен. Каждое попадание в `RW_TB_OUTBOUND_BLOCK` видно в access.log с email пользователя, а SubGate этот лог уже собирает.

## 3. nDPI и шейпер SubGate — удалить

- **TC/TBF-шейпер.** Требует отдельный сетевой интерфейс на каждого пользователя (`agent/internal/worker/config.go`). В Xray все пользователи выходят с одного IP ноды через общие inbound'ы, поэтому на ваших нодах шейпер в принципе не может ограничить конкретного пользователя.
- **nDPI-коллектор на C.** Требует Ethernet DLT. Видит потоки нода→пир без привязки к пользователю, шифрованный BT и трафик через WARP/мосты не классифицирует. Тянет libndpi, libpcap и отдельный бинарник ~18 МБ.
- **Из worker нужно сохранить** только замер нагрузки интерфейса для анализа перегрузки (`analysis/overload.go`). Это переносится в обычный агент чтением `/proc/net/dev`, без C и без отдельного сервиса.

Решение: удалить worker, nDPI и шейпер (~2 тыс. строк). Вместо них сделать детектор и действия ниже.

## 4. Предлагаемая защита

Принцип: **детект по пользователю из access.log, действие через API панели, никаких IP-банов.** Всё, что нужно для детекта, агент уже присылает: email, назначение, порт, сеть, inbound/outbound tag.

### 4.1 Сигналы (окно 1 минута на пользователя и ноду)

| Сигнал | Правило по умолчанию | Сила |
|---|---|---|
| `torrent_block_hit` | Соединение ушло в outbound из списка, по умолчанию `RW_TB_OUTBOUND_BLOCK` (теги можно добавить) | сильный |
| `p2p_fanout` | ≥ 25 разных IP-литералов назначения **и** ≥ 20 разных портов, ≥ 70% портов > 1024, при этом ≥ 60% назначений — IP без домена (при включённом sniffing браузинг идёт по доменам, пиры — по голым IP). Повтор в 2 из 5 минут | средний |
| `udp_fanout` | ≥ 30 разных UDP-назначений по IP-литералам в минуту (DHT, uTP) | средний |
| `scan_suspect` | ≥ 100 разных IP на один порт из списка (22, 23, 445, 3389, 5900…) или ≥ 200 пар ip:port в минуту | сильный (жалобы хостера) |
| существующие `connection_rate`, `destination_breadth`, `port_breadth` | без изменений | — |
| (опц.) отчёт torrent-blocker из API панели | опрос `GET /api/node-plugins/torrent-blocker`, сопоставление по `userId` | сильный |

Защита от ложных срабатываний:
- allowlist пользователей (например, тег `SERVICE`) и назначений;
- порог «2 из 5 минут» для средних сигналов;
- в инциденте хранятся доказательства (топ назначений, порты, outbound tags) со ссылкой в журнал.

### 4.2 Действия (лестница, по умолчанию «только уведомлять»)

1. **Инцидент в консоли + сообщение в Telegram.** Отправка по инцидентам появится на этапе B. Переменные `SUBGATE_TELEGRAM_*` для настройки уже добавлены в этой ветке.
2. **Разрыв соединений:** `POST /api/connections/drop` для пользователя. Клиент переподключится; эффективно против кратких сессий.
3. **Временное отключение:** `POST /api/users/{id}/actions/disable` на N минут, затем SubGate сам вызывает `enable`. Таймер хранится в БД и переживает рестарт; каждое действие пишется в аудит.
4. Повторные срабатывания увеличивают срок отключения: 15 мин → 1 ч → 24 ч. Сделать постоянную блокировку может только владелец, вручную из консоли.

Ступени 2–4 включаются политикой и требуют `allow_writes: true` и токена с правами `connections:drop` и `users:disable/enable`. Режим «dry-run» показывает, что было бы сделано. Middleware при этом не трогается: он увидит отключённого пользователя через панель, как и при ручном отключении.

### 4.3 Рекомендации по нодам (без кода)

- Включить плагин torrent-blocker и добавить в `includeRuleTags` правила по портам 6881–6889 и доменам трекеров. SubGate будет видеть эти попадания как `torrent_block_hit`.
- Проверить, что в отчётах плагина `source` — не `127.0.0.1`. Если перед Xray стоит nginx/haproxy stream без proxy_protocol, баны по IP бесполезны.
- Держать включёнными sniffing и access.log с email. Без них детект по доменам и пользователям не работает.

### 4.4 Этапы реализации

| Этап | Содержание | Объём |
|---|---|---|
| A | Удалить worker, nDPI и шейпер; перенести замер интерфейса в агент (`/proc/net/dev`); анализ перегрузки оставить | ~−2000 / +150 строк |
| B | Сигналы `torrent_block_hit`, `p2p_fanout`, `udp_fanout`, `scan_suspect` в `core/internal/analysis` + политика + UI-подписи + Telegram-уведомление по инциденту | ~+500 строк с тестами |
| C | Лестница действий через API панели (drop → disable → auto-enable), dry-run, аудит, кнопки в карточке инцидента | ~+400 строк с тестами |
| D (опц.) | Опрос отчётов torrent-blocker из панели как подтверждение | ~+150 строк |
| E (опц., позже) | Сигнатуры DHT, uTP и UDP-трекера в nftables на OUTPUT ноды (идея из vibehost-guard) с сопоставлением с access.log по `ip:port` и времени. Нужен `NET_ADMIN` у агента | отдельная задача |

Рекомендованный порядок: A → B → C. Пороги из 4.1 стоит неделю погонять в режиме «только уведомлять» на реальном трафике, потом включить действия.
