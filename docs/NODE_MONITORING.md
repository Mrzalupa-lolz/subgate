# nDPI, перегрузка и временный shaper

Дополнительный Linux-процесс `subgate-worker` работает рядом с обычным Agent. Agent продолжает собирать Xray StatsService и access.log; worker собирает счётчики интерфейса/CPU, запускает отдельные процессы nDPI и выполняет ограниченные TC-команды. Токен панели worker не получает. Внешние HTTP-сервисы он не открывает.

## Атрибуция

Обычный Xray access.log не содержит достоверной связи исходящего сокета с аккаунтом. После NAT или multiplexing такую связь нельзя восстановить по общему IP. Поэтому для автоматического shaper реализован конкретный режим: выделенный сетевой путь аккаунта с отдельными интерфейсами (например, veth/netns с Ethernet capture). Коллектор принимает Ethernet capture; raw TUN и Linux cooked capture не поддержаны. Xray и маршрутизация должны уже направлять внутренний, расшифрованный трафик этого аккаунта через этот путь. Worker не меняет маршрутизацию и не создаёт такие пути автоматически.

Оператор задаёт `bindings`: канонический UUID Remnawave, интерфейс захвата, до двух выделенных интерфейсов для ограничения направлений, `exclusive`, `valid_from`, `expires_at`. Общий интерфейс допустим для наблюдения с `exclusive:false` и пустыми `shape_interfaces`; санкций для него не будет. Привязки нужно продлевать атомарной заменой файла. При смене аккаунта на интерфейсе обновляют `valid_from` и перезапускают worker; прежние потоки не переатрибутируются. Изменение набора захватов требует перезапуска; срок привязки и локальные исключения перечитываются во время работы.

Нельзя указывать публичный интерфейс ноды в `shape_interfaces`: worker откажет для `resource_interface`. Владелец конфигурации отвечает за эксклюзивность остальных устройств. TC затрагивает весь трафик выделенного устройства, поэтому общий uplink нельзя объявлять выделенным. На одном worker поддерживается до 64 захватов; предел не является подтверждённой производственной ёмкостью.

## Сборка

Core/Agent остаются Go-программами без CGO. Дополнительный коллектор — небольшой C-процесс с динамической libnDPI/libpcap. Проверены nDPI 4.14.0 и 4.2.0; для автоматики BitTorrent используйте 4.14.0: версия 4.2 помечает сигнатуры как cache inference и остаётся для них только источником наблюдений. Версии с другим API требуют отдельной проверки.

Пример для Ubuntu/Debian, из корня репозитория:

```sh
sudo apt-get update
sudo apt-get install -y build-essential pkg-config libpcap-dev libgcrypt20-dev autoconf automake libtool git
git clone --depth 1 --branch 4.14 https://github.com/ntop/nDPI.git /tmp/subgate-ndpi-4.14
cd /tmp/subgate-ndpi-4.14
# Проверенный tag 4.14: 90090b9ae841fce67d00c52ac87e755dcea7c95f
autoreconf -fi
./configure --prefix=/usr/local --with-only-libndpi
make -j4
sudo make install
sudo ldconfig
cd /path/to/subgate
make build-worker
PKG_CONFIG_PATH=/usr/local/lib/pkgconfig make -B build-ndpi
python3 test/ndpi_smoke.py
sudo install -m 0755 bin/subgate-worker agent/native/subgate-ndpi /usr/local/bin/
```

Файлы библиотеки и бинарников должны быть недоступны для записи пользователям VPN. Процесс коллектора после открытия capture сбрасывает UID/GID и все capabilities, устанавливает `no_new_privs`. Нужные пакеты анализируются в памяти; stdout содержит только ID, протокол, уверенность, версию, время, объёмы, потери и неполноту. Адреса, домены, payload, URL, SNI, infohash и содержимое пакетов в Core не отправляются. Неизвестные/зашифрованные потоки остаются неизвестными. IPv4/IPv6 TCP/UDP поддерживаются; фрагменты, IPv6 extension headers и переполнение таблицы явно снижают качество и запрещают автоматическое решение.

## Подключение

```sh
sudo install -d -m 0700 /etc/subgate
sudo install -m 0600 deploy/worker.json.example /etc/subgate/worker.json
# Отредактируйте core_url, node_id, token_file, ёмкость и реальные bindings.
sudoedit /etc/subgate/worker.json
sudo install -m 0644 deploy/subgate-worker.service deploy/subgate-worker-expire.service deploy/subgate-worker-expire.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now subgate-worker-expire.timer subgate-worker.service
```

Пример содержит просроченную привязку и не может автоматически ограничить аккаунт. `expires_at` задают не дальше суток от текущего времени и продлевают до истечения; `valid_from` сохраняют, пока эксклюзивный путь принадлежит тому же аккаунту. Ёмкость `capacity_mbps` задают по известной ёмкости выбранного `resource_interface`, а не по сумме счётчиков пользователей. `token_file` — токен уже зарегистрированного обычного Agent; при Docker укажите доступный на хосте файл из его volume. Конфигурация должна быть приватным обычным файлом (0600), принадлежащим root. Настройки Core находятся в «Правила анализа»: лимит, срок, переключатель автоматики, точные имена ограничиваемых протоколов и UUID исключений. Начальное состояние: автоматика выключена, лимит/срок/список протоколов не заданы.

## Условия решения

- Последовательные полные минуты загрузки интерфейса выше порога: по умолчанию 85% ёмкости, 3 минуты. Минуте нужны минимум 45 секунд покрытия. Пропуски, потери, смена ёмкости и устаревшие данные разрывают подтверждение. Для восстановления нужны две минуты ниже 70%; исторический EWMA baseline и CPU показываются как контекст, а не доказательство нарушения.
- Два разных потока одного явно ограничиваемого протокола в двух UTC-минутах за последние 3 минуты. Только уверенность nDPI `dpi`: port/IP/cache guesses не допускаются. Один долгий поток или перепакованный отчёт не заменяет два независимых потока.
- Синхронизированный канонический аккаунт и действующая эксклюзивная привязка на весь TTL; неоднозначные алиасы Xray исключаются. Потоки до начала привязки или с потерянной атрибуцией не становятся доказательством задним числом.
- Независимые счётчики Xray: минимум 45 секунд качественного покрытия последней завершённой минуты и минимум 35% загрузки ноды в одном направлении. Inbound fallback, gap, warming и перекрывающиеся отсчёты не допускаются.
- Явно включённая политика, ненулевые лимит и срок, отсутствие аккаунта в исключениях. Большой легитимный расход без ограничиваемого протокола остаётся наблюдением. Ручной статус «подтверждено» сам по себе не запускает TC.

Независимые источники здесь — пакетный коллектор, интерфейсные счётчики ядра и Xray StatsService. Несколько правил из одного access.log независимым подтверждением не считаются.

## Исполнение, TTL и отмена

Core атомарно сохраняет зашифрованную команду и аудит. Worker получает только команды своей ноды, проверяет часы (расхождение до 5 секунд), локальные привязки и allowlist, сохраняет намерение в fsync-журнале и применяет TBF с зарезервированным handle `7a11:`. На каждом указанном направлении действует лимит `shaper_mbps`; это лимит направления, не общий пул двух направлений. Существующий чужой root qdisc не заменяется. Частичная установка откатывается; неудачная очистка остаётся в журнале для повторной попытки. Повторная доставка не продлевает TTL.

Основной цикл удаляет истёкшие ограничения. Отдельный `subgate-worker-expire.timer` проверяет журнал каждые 5 секунд даже при недоступном Core или остановленном worker; `ExecStopPost` снимает ограничения при остановке/аварии сервиса. TC сам не имеет TTL: независимый systemd timer обязателен. Задержка снятия ограничена периодом таймера и временем выполнения TC при исправном ядре/systemd; ошибки удаления видны в journal и повторяются. Перезагрузка ядра сама удаляет qdisc. Остановка systemd/полный зависший хост не дают гарантии wall-clock TTL.

Кнопка «Снять», выключение автоматики, исключение аккаунта или удаление протокола из политики убирают команду из желаемого состояния. При доступном Core worker снимает её в следующем цикле, обычно за 10 секунд; при недоступном Core действует прежний абсолютный TTL. Локальный allowlist работает без Core. Фактические статусы `applied`/`removed`/`failed` подтверждает нода; `cancelled` означает запрос снятия, `expired` — прошедший срок без обязательного подтверждения удаления.

Аварийное локальное снятие:

```sh
sudo /usr/local/bin/subgate-worker -config /etc/subgate/worker.json -cleanup
```

Новые таблицы Core используют существующий механизм ключей, шифрования и backup. Наблюдения хранятся 14 дней; текущие DPI-метаданные — до 5 минут при поступлении отчётов, до 10000 потоков на ноду. Команды и их аудит сохраняются для разбора. Проект не развёртывается автоматически этими изменениями.
