## 7. Вопросы владельцу

Эти вопросы не мешали аудиту; до решений соответствующие расширения не реализовывать.

1. **F21 и F27:** v4 §4.2/§17 исключают reimplementation detectors/Xray editor, inventory Part B их добавляет, а текущая цель — замена remnawave-admin. Какие analyser/editor возможности входят в первую версию? Коннектор уже исключён текущим поручением, повторного разрешения на него не требуется.
2. **Внешние сервисы:** фраза «единственные внешние интеграции — Remnawave и VPN-ноды» как применяется к Telegram, email, S3, IP-intel feeds, Bedolaga/CRM и remote release downloads из исходных требований? Предметных связей с admin не планируем; перечисленные delivery/data services требуют явного scope-решения.
3. **Part A inventory:** это только референс для Part B или нужно весь каталог чужих продуктов (mail/Android/CRM/all installers/etc.) воспроизвести в SubGate? Part B заменяет Android на PWA; v4 исключает billing и тяжёлое panel editing. Нужен согласованный v1/optional список, без догадок.
4. **Квоты vs fail-open:** источник требует исключить exhausted node, текущий тест закрепляет original subscription. Какой вариант при исчерпании **всех** eligible nodes: serve all/panic с alert либо другая явно согласованная политика? Для одной exhausted node с живым fallback требование F6 однозначно не выполнено.
5. **Panel discovery:** локальный spec3.4.5 — какая версия реально установлена; какие client apps/sub formats, объём users/nodes и допускаемые API scopes? Не присылайте секреты в чат; для будущей проверки достаточно версии и способа безопасного предоставления test credentials.
6. **Activity defaults/privacy:** v4 требует journaling enabled by default, retention14/90/365, отдельные superadmin permissions, backup exclusion. Подтвердить группы/исключения/legal hold/реальный disk budget; agent log enrichment должен происходить без payload и production raw corpus leakage.
7. **Технологический контракт:** v4 Go1.24+/Linux-only/linux tags/ogen/Preact/gRPC-or-WS+zstd/columnar store; сейчас Go module1.25, regular Windows paths, manual client, vanilla JS, HTTP JSON, SQLite events. Сохранять буквальный стек или принимать отклонения только после ADR/benchmarks? Для unsigned local installer/изменённого storage раньше согласованного ADR не найдено.
8. **Синхронизация и история identity:** v45min+jitter против текущего1min; webhook freshness <=1s пока только cache invalidation. Какой sync SLA/нагрузка допустимы и как хранить immutable user identity aliases для rename/revocation?
9. **Релиз:** сохраняем кодовый номер0.2.0 без production-ready claim; какой набор v1 requirements/load/Linux/real-Xray/fail-open checks должен пройти для реального релиза?
10. **Обязательные старые документы в v4:** он требует ASSUMPTIONS/ADRs/design и остановки на P0, текущее поручение требует их удалить/объединить. Для этого аудита применено ваше более новое прямое поручение; все последующие решения/assumptions ведём здесь до вашего изменения правил.

## Ответы владельца (2026-10-13)

Q1 (F21, детекторы злоупотреблений): в v1 только сигнал, без автодействий
  (никаких автоблокировок и автоотключений). В каждом сигнале обязательно
  указывать, в чём именно обвиняется пользователь и на основании каких
  признаков (конкретные данные и пороги) сделан вывод, чтобы его можно было
  проверить вручную.

Q1 (F27, Xray-редактор): входит в v1. Не графический, а текстовый редактор
  конфига Xray в веб-интерфейсе («просто пишешь и всё»), со всем перечисленным:

- подсветка синтаксиса;
- автодополнение;
- проверка конфига перед применением;
- при наведении на параметр (например xhttpSettings) показывается его
  документация: описание, аргументы, допустимые значения, как подсказки в IDE.
  Документация привязана к версии Xray на нодах (сейчас 26.7.28).

Q2 (внешние сервисы):
  а) Telegram-уведомления: да
  б) email: нет
  в) S3: нет
  г) скачивание баз IP/ASN: да
  д) скачивание обновлений данных (документация Xray для редактора, базы ASN/IP
     и подобные обновляемые данные): да. Самообновление самого SubGate
     (скачивание и подмена бинарника) не входит.
  Для редактора копия документации Xray должна быть встроена в сборку как
  запасной вариант (чтобы редактор работал без интернета).

Q3: делать только Part B. Part A (каталог чужих продуктов) это справочник идей,
  воспроизводить его не нужно.

Q4 (квоты): если трафик закончился на конкретной ноде, убирать её хост из
  подписки пользователя и добавлять вместо него заглушку вида
  «<флаг страны> У ВАС ЗАКОНЧИЛСЯ ТРАФИК». Если лимиты закончились на всех
  нодах пользователя, не реализовывать: заглушку «лимит исчерпан» отдаёт сам
  Remnawave. Проверить это; если он её на самом деле не отдаёт, вынести вопрос
  мне, самому решение не принимать.

Q5 (панель и окружение):

- Remnawave panel 3.4.5, remnanode 3.4.2, Xray 26.7.28, всё самые свежие на
  2026-10-13. Схема remnawave-openapi.json v3.4.5 соответствует панели.
- Проект коммерческий. Клиентские приложения: Happ и Incy; также нужна
  поддержка формата mihomo.
- Ноды: 6 (NL, PL, FI, FR, EE, DE). Панель стоит на FR-ноде. FI-нода
  используется только для whitelist-логики.
- Нагрузка: примерно 100 пользователей, пик примерно 100 одновременных
  подключений.
- Единственная панель боевая. Ключ API, выдаваемый на время разработки,
  только для чтения. Любую запись в панель (редактор конфигов и т.п.)
  проверять только на отдельной тестовой панели, которую поднять на тестовом
  Linux-сервере. Ключ с правом записи для эксплуатации выдаётся отдельно
  после разработки.

Q6 (активность, права):

- Журнал активности включён по умолчанию.
- Хранение: 7 дней в полном объёме, дальше сильное сжатие в архив, через
  90 дней удаление с диска.
- Бюджет диска под журнал: 50% свободного места на момент развёртки SubGate.
- Учётная запись одна, с полным доступом ко всему. Ролей, групп и отдельных
  прав superadmin не делать. Вход только логин и пароль, без 2FA.

Q7 (технологии): сервис только под Linux, совместимость с Windows не нужна.
  Язык Go. Приоритет скорость и надёжность, минимум промежуточных слоёв, прямой
  и быстрый обмен данными, но надёжность важнее. Текущий стек (Go 1.25, JS без
  Preact, SQLite, HTTP JSON) оставляем; менять только если он подтверждённо
  медленнее или менее надёжен.

Q8 (синхронизация): изменения пользователей подтягивать по вебхукам Remnawave;
  лимиты, ключи и всё, что вебхуки не покрывают, опрашивать раз в минуту.
  Пользователя в панели переименовать нельзя, поэтому история имён не нужна.

Q9 (релиз): готово, когда все функции реестра, входящие в согласованный scope
  (то есть без исключённого: email, S3, самообновление SubGate, автодействия
  по обвинениям, Part A), выполнены на 100% (статус DONE с доказательством).

Q10: подтверждаю. Старые документы удалены, единый план это
  docs/PROJECT_PLAN.md, решения и допущения ведём в docs/DECISIONS.md.
