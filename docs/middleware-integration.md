# SubGate и Remnawave Subscription Middleware

Решение от 2026-10-31: функции выдачи дополнительных конфигов и управления пользователями обслуживает `remnawave-subscription-middleware`. SubGate отвечает за инфраструктурную маршрутизацию и данные агентов. Сверка выполнена по локальному каталогу `remnawave-subscription-middleware/`, включая PHP-реализацию; middleware в рамках этой работы не развёртывался.

## Что вынесено из активного SubGate

| Функция                                                                              | Где реализована в middleware                                                  | Что изменилось в SubGate                                                                                                                                  |
| ------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Добавление конфигов к подписке                                   | `lib/squadconf.php`, `lib/vless.php`, `lib/addsub.php`                                 | Инъекции `append/prepend/patch/remove`, полные `xray-profile`, API `/injections`, редактор и тесты перенесены в архив |
| Включение/отключение пользователя, сброс трафика | `lib/users_admin.php`: `ua_action`, `remnawave_user_post`, `remnawave_reset_traffic` | Убран `POST /api/v1/users/{id}/actions/{action}`, кнопки действий; `panel.Client.Action` принимает только nodes                   |

Это пересечение по назначению. Middleware создаёт дополнительные WG/AWG/VLESS-конфиги по сквадам, учитывает статус пользователя и возможности клиента. Произвольный полный Xray JSON, JSON Pointer и операции patch/remove из SubGate не имеют точного эквивалента в middleware. Они сохранены вместе с прежним модулем; при необходимости их можно вернуть. Автоматического преобразования правил нет.

Оригиналы: [архив и возврат](../_archive/middleware-overlap-2026-10-31/README.md). Общие файлы сохранены целиком перед правками; отдельные Go-модули и тесты перенесены с расширением `.disabled`. Старые записи `sg_objects(kind='injections')` и таблица `injections` остаются в SQLite, но не читаются при выдаче подписки. Миграции и пользовательские данные не удаляются.

## Что остаётся в SubGate и почему

- Tiers, policies, pins, fallback, health-проверки и карантин: выбирают ноды по состоянию инфраструктуры и данным агентов.
- Квоты по пользователю/ноде: считают подтверждённую телеметрию, а не только лимит подписки в панели.
- Агенты, Xray StatsService/access.log, скорость, история трафика, активность и SSE: дают собственные измерения. Панельные суточные графики middleware их не заменяют.
- IP/ASN-данные, geo-правила и anti-scan с tarpit/deny: используются для маршрутизации и защиты. Фильтр длины shortUuid и журнал мусорных URL в middleware не заменяют этот механизм.
- Диагностика нод, управление нодами, бэкапы БД SubGate, авторизация консоли, аудит и метрики: обслуживают сам SubGate.
- Приём вебхуков панели: обновляет локальный снимок и сбрасывает кеш. Это отдельный потребитель, которому middleware может переслать событие, а не второй механизм fan-out.
- Gateway/кеш/разбор форматов: обеспечивают применение инфраструктурных решений к подписке. Удаление gateway отключило бы балансировку и карантин.

## Как подключать

Для общего домена подписки возможна схема в режиме зеркала middleware:

```text
VPN-клиент → middleware → HTTPS origin SubGate → сервис подписок Remnawave
                    ↘ API панели Remnawave
```

Middleware проверяет устройство, пишет клиентский лог и добавляет свои конфиги к ответу после маршрутизации SubGate. В middleware задаётся origin-домен SubGate, а `SUBGATE_SUBSCRIPTION_URL` / `panel.subscription_url` указывает прямо на сервис подписок Remnawave. Он должен принимать `/{shortUuid}[/{clientType}]` относительно указанной базы; стандартный backend использует `/api/sub`. Не направляйте origin обратно на middleware: получится цикл. Режим middleware «основная подписка», который сам читает `/api/sub` панели, такую цепочку обходит.

Настройте передачу исходного IP доверенным reverse proxy и соответствующие CIDR `http.trusted_proxies` SubGate перед использованием geo/ASN/anti-scan. Проверьте GET/HEAD, форматы клиентов и HWID на своей конфигурации. Приведённая схема описывает подключение, но не означает выполненную проверку двух сервисов в Docker или с живой панелью.

Если SubGate используется только для наблюдения, публичный домен подписок можно направить сразу на middleware; gateway SubGate тогда не участвует и его policies/pins/квоты не влияют на выдачу.

Для синхронизации оставьте прямой API-токен панели в SubGate. Если включён fan-out middleware, укажите SubGate `/webhook/panel` отдельным получателем с собственным секретом и переподписыванием. При настройке nginx fallback используйте тот же сервис подписок, что и upstream SubGate; пример fallback обращается к `/api/sub`.

Изменение исходников не развёртывает middleware, не меняет DNS/секреты и не переносит правила из существующей базы. До следующего запуска новой версии SubGate действующие процессы продолжают использовать прежний бинарник.
