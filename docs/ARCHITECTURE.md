# Как устроен SubGate

SubGate собирает телеметрию Remnawave и Xray, показывает состояние нод и помогает разбирать аномалии. Подписки и управление подписчиками обслуживает отдельный `remnawave-subscription-middleware/`; внешнюю DDoS/firewall-защиту выполняют скрипты на нодах.

```text
Remnawave API → Core ← Agent на каждой VPN-ноде
                 ↕       Xray StatsService + access.log
           SQLite + веб-консоль
                 ↑
       дополнительный Linux worker: nDPI, нагрузка, TC/TBF

VPN-клиент → middleware → сервис подписок Remnawave
```

Core и Agent написаны на Go, используют HTTP JSON; консоль получает live-снимки через SSE. SQLite работает в WAL без CGO. Worker устанавливается отдельно; нативному коллектору нужны libnDPI и libpcap.

## Панель и идентификация

Core синхронизирует пользователей и ноды. Пользователи нужны для сопоставления телеметрии с аккаунтами. Снимок публикуется атомарно; при ошибке остаётся последний успешный. Источник изменений один — периодический опрос панели, по умолчанию раз в минуту; webhook-приёмника нет. Состояние ноды (isConnected/isDisabled, usersOnline) берётся из этого опроса, живость агента — из heartbeat.

Токен панели хранится только в Core. По умолчанию клиент разрешает только GET, запрещает перенаправления и ограничивает ответ 16 MiB. Проверка версии при старте имеет бюджет 3 секунды; несовпадение версии видно в статусе и не останавливает мониторинг. Подробности: [контракт Remnawave](panel-contract.md).

Метки Xray сопоставляются с числовым id, username, email и short UUID только при однозначной принадлежности. Неизвестные метки остаются доступны в журнале. Общий IP не доказывает принадлежность трафика аккаунту.

## Agent и доставка

Agent регистрируется одноразовым токеном на 15 минут и получает отзывной токен ноды. Он не открывает входящий HTTP-порт. Повторная регистрация заменяет прежний токен.

StatsService всегда читается с `reset=false`. Скорости вычисляются по разнице счётчиков и времени; после перезапуска действует прогрев. При отсутствии пользовательских счётчиков используется явно обозначенный inbound fallback.

Agent читает `access.log` с конца файла. Нужны email пользователя в Xray и доступ к файлу на чтение. StatsService ищется через локальный abstract Unix socket или loopback; Docker socket агенту не нужен.

Очередь шифруется ключом, связанным с токеном и нодой. Пакет сохраняет ID и время создания при повторной доставке и перезапуске. Максимум очереди — 16 MiB, пакета Agent — 5000 измерений, 1000 событий и 2 MiB. Сеть, 408/429/5xx вызывают повтор; постоянные validation 4xx удаляют отвергнутый пакет со счётчиками потерь; 401/403 останавливают агент с сохранением очереди. Логи до помещения в очередь остаются в памяти. При замене токена старая очередь новым ключом не расшифруется.

## Анализ и ограничения

Core формирует наблюдения по числу записей Xray, IP назначения и портов одного назначения за UTC-минуту. Начальные пороги — 3000/512/128 соответственно. События старше двух минут остаются в журнале, но не создают текущие наблюдения. Есть дедупликация, ограничения памяти и признак неполноты `truncated`. Решение и заметка владельца сохраняются с аудитом.

Дополнительный worker сопоставляет nDPI, длительную перегрузку и независимые счётчики Xray. Автоматический TC/TBF требует выделенных интерфейсов аккаунта, действующей эксклюзивной привязки и явной политики. Автоматика изначально выключена; подтверждение наблюдения вручную само по себе не запускает ограничение. Условия, сборка и TTL: [мониторинг ноды](NODE_MONITORING.md).

## Данные и безопасность

Одна учётная запись владельца с логином и паролем. Сессии хешируются в SQLite; cookie имеют HttpOnly/SameSite Strict и Secure при HTTPS. Изменения через cookie требуют CSRF и проверки Origin. Журнал, наблюдения и чувствительные детали аудита шифруются AES-GCM. Ротация ключей требует перезапуска: один активный ключ и до восьми прежних; автоматического перешифрования нет.

Журнал содержит metadata назначения host:port, а не посещённые URL или содержимое трафика. Поиск и CSV/JSON export ограничены размером выборки; domain-фильтр работает по этой выборке. Чтение и экспорт аудируются и делят бюджет 60 запросов в минуту на владельца. При недоступном аудите данные не выдаются.

Сырые таблицы скоростей (sg_speed, sg_speed_meta, sg_usage) очищаются через 24 часа; buckets вычисляются при чтении, поэтому запрос за 31 день не означает хранение данных за 31 день. Журнал активности хранится 14 дней (`hot_ttl`), наблюдения — 14 дней (UI показывает последние 200), журнал аудита — 180 дней, действия shaper — 30 дней после истечения, шифрованных резервных копий сохраняется 14 последних. Политика длительного хранения журнала и её незакрытые части описаны в [решениях](DECISIONS.md) и [плане](PROJECT_PLAN.md).

Локальный IP lookup читает JSON prefixes/MMDB, использует longest-prefix match и сохраняет последний успешный набор при неудачном reload. Автоматического скачивания/сборки баз и карты origins пока нет. Сведения о стране и ASN не доказывают физическое местоположение человека.

Локальные `.sgb` backups содержат снимок SQLite, включая activity; для восстановления нужен исходный ключ. [Резервирование и восстановление](DEPLOYMENT.md#восстановление-резервной-копии-через-docker).

## Граница с middleware

В Core отсутствуют `/sub/...`, короткие aliases подписок, request-signals, injections, tiers/policies/pins, geo-rules и пользовательские mutations. Старые строки SQLite остаются неактивными. `SUBGATE_SUBSCRIPTION_URL` больше не читается. Домен подписок должен вести к middleware; настройка DNS и миграция правил выполняются отдельно.

Исходники снятого контура остались в истории git: тег `pre-cleanup-2026-11-09`. Middleware — отдельный проект со своим репозиторием и деплоем; SubGate с ним не синхронизируется.
