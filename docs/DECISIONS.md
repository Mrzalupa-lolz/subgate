# Принятые решения

Актуальные границы на 2026-11-01. Уточнения владельца о мониторинге и условной автоматике заменяют ранний запрет любых автоматических ограничений. Эта страница описывает требования; наличие реализации проверяется по коду и [плану](PROJECT_PLAN.md).

## Назначение продукта

- SubGate работает с Remnawave, телеметрией нод и внутренними логами Xray. Целевой масштаб мониторинга — до 20 нод и 1000 активных аккаунтов; ёмкость ещё нужно подтвердить.
- Подписки, пользовательские операции, устройства/HWID/UA, grace, клиентские конфиги и страницы обслуживает отдельный middleware. SubGate не участвует в цепочке выдачи подписок и не изменяет их при исчерпании аналитической квоты.
- Внешние DDoS/firewall-меры остаются скриптам нод. Коннектор remnawave-admin не разрабатывается.
- Linux, Go, SQLite, HTTP JSON/SSE, vanilla JavaScript. Изменение стека требует измеренной причины по скорости или надёжности.

## Анализ и временное ограничение

Большой расход, общий IP, множество соединений и метка P2P по отдельности не доказывают нарушение. Наблюдение должно показывать измерение, порог, время, аккаунт, ноду и ограничения качества, чтобы владелец мог его проверить.

Владелец разрешил автоматическое временное ограничение при высокой уверенности; остальные случаи идут на ручной разбор. Нужны повторные независимые подтверждения, точная атрибуция и контроль качества источников. Лимит, срок, протоколы и исключения задаёт владелец. По умолчанию автоматика выключена, лимит/срок не заданы, список протоколов пуст.

Согласован отдельный nDPI-коллектор с минимальными правами. Он передаёт в Core классификацию и счётчики без payload. Реализация использует выделенные интерфейсы аккаунта с временной эксклюзивной привязкой, TC/TBF и независимый systemd TTL watchdog. Это выбранный способ реализации, а не обещание атрибуции на любой общей Xray-ноде. [Точные условия](NODE_MONITORING.md).

## Доступ и данные

| Решение | Требование |
| --- | --- |
| Владелец | Одна учётная запись с полным доступом, логин/пароль; без ролей, групп и 2FA |
| Рабочая панель | При разработке только GET. Запись проверяется на отдельной тестовой панели; клиент по умолчанию read-only |
| Синхронизация | Webhooks для изменений пользователей, остальное — опрос раз в минуту; история имён не требуется |
| Xray | StatsService всегда `reset=false`; destinations только host:port, без URL и содержимого трафика |
| Журнал | Включён по умолчанию; 7 дней полностью, затем сильное сжатие, через 90 дней удаление; бюджет 50% свободного диска при развёртывании |
| Внешние сервисы | Telegram и обновления данных IP/ASN/Xray docs разрешены; email, S3 и самообновление бинарников SubGate исключены |
| Xray-редактор | Текстовый: подсветка, completion, проверка перед применением и hover-документация для версии Xray; встроенная offline-копия обязательна |

Политика журнала реализована не полностью: текущие SQLite rows и retention-настройки не обеспечивают требуемые сжатые tiers и дисковый бюджет. Срок наблюдений анализа 14 дней относится к отдельным сущностям и не заменяет политику журнала.

Legal hold сверх 90 дней и дополнительные группы capture остаются открытыми вопросами. До отдельного решения сроки не расширяются, дополнительные роли не вводятся. Optional fleet/support/plugin-функции не становятся обязательным этапом без уточнения scope.

## Контракты и готовность

Исходная схема Remnawave — 3.4.5; ранее проверявшиеся Remnanode/Xray — 3.4.2/26.7.28. Эти версии являются опорой контракта, а не утверждением о текущих версиях рабочей инфраструктуры. [Контракт и проверка расхождений](panel-contract.md).

Функция готова после проверки согласованного поведения с assertions/PASS или воспроизведённой ручной проверкой. Старый PASS, пропущенный live-тест и наличие вспомогательной utility не доказывают текущую готовность. Текущие задачи ведутся в одном [плане](PROJECT_PLAN.md), прежние формулировки доступны в истории Git.
